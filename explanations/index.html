EduCore LMS Front-End Documentation

A comprehensive guide for the front-end team to understand the UI, logic, and architecture.

1. Front-End Overview

What the UI does

The EduCore front-end is a role-based Learning Management System designed to serve Students, Instructors, and Administrators. It provides a highly interactive and visually premium interface (using "glassmorphism") to manage courses, assignments, grades, system logs, and users.

Main features available to the user

  • Students: View enrolled courses, submit assignments, track grades, and participate in course discussions.
  • Instructors: Create courses, organize lectures, grade assignments, and make announcements.
  • Administrators: Manage users (CRUD), view system logs, configure platform settings, and generate reports.

Type of App & Tech Stack

  • Type Single Page Application (SPA)
  • Framework React 19 (JavaScript)
  • Styling Tailwind CSS v4 (Vanilla CSS utility classes)
  • Routing React Router DOM
  • Build Tool Vite

src/ ├── components/ # Reusable UI elements │ ├── ui/ # Generic buttons, cards, inputs │ └── ProtectedRoute.jsx # Role-based access wrapper ├── context/ # React Context for global state │ └── AuthContext.jsx # Manages user login/logout & roles ├── layouts/ # Page wrappers with navigation bars │ ├── AdminLayout.jsx │ ├── StudentLayout.jsx │ └── InstructorLayout.jsx ├── pages/ # Individual screens organized by role │ ├── admin/ # Admin-only pages │ ├── auth/ # Login & Registration │ ├── instructor/ # Instructor views │ ├── student/ # Student views │ ├── messages/ # Shared inbox │ └── notifications/ # Shared notifications ├── App.jsx # Main routing hub ├── main.jsx # Application entry point └── index.css # Global Tailwind & vanilla CSS styles

Purpose Breakdown

  • pages/views: Each file represents a full screen viewed by the user. Grouped by user role to enforce separation of concerns.
  • components: Modular, stateless (or localized state) UI blocks. Minimizes code duplication.
  • layouts: Wraps pages with headers, sidebars, and ambient backgrounds specific to the user's role.
  • scripts/context: Handles logic that needs to be shared across the entire app (e.g., who is logged in).

Auth Pages (Login & Register)

Purpose: Serves as the security gate. Validates credentials and assigns roles.

4. Components Breakdown

1. Card <Card />

  • Responsibility: Provides a consistent, glassmorphic container for content blocks.
  • Props: children, className, hover (boolean to enable hover effects).
  • Reusability: Extremely high. Used on almost every dashboard and list page.

2. Input <Input />

  • Responsibility: Standardized text and email input fields handling labels, errors, and icons.
  • Props: label, id, type, error (string for validation feedback), icon, onChange.
  • Reusability: High. Included in Auth forms and Modal dialogs.

3. ProtectedRoute <ProtectedRoute />

  • Responsibility: Checks the AuthContext. If a user tries to access a route they don't have permission for, it redirects them.
  • Props: allowedRoles (array of strings, e.g., ['student', 'admin']).
  • Where used: Directly inside App.jsx wrapping the route definitions.

5. UI Logic & Interactions (CORE)

Form Handling & Validation

In React, form inputs are controlled using component State. When a user submits, we intercept the event, validate, and then update the UI.

const validate = () => {
    const newErrors = {};
    if (!email) {
      newErrors.email = 'Email is required';
    } else if (!/\S+@\S+\.\S+/.test(email)) {
      newErrors.email = 'Please enter a valid academic email address';
    }
    
    setErrors(newErrors);
    return Object.keys(newErrors).length === 0;
};

const handleSubmit = (e) => {
    e.preventDefault(); // Prevents page reload
    if (!validate()) return; // Stops submission if invalid
    
    // Proceed with login logic
    login(role);
};

Step-by-step: The user types in an input (triggering onChange and updating the email state). Clicking submit triggers handleSubmit. It runs validate(), which populates the errors state if criteria aren't met, causing the UI to re-render in red with error messages.

State Changes & CRUD Operations

For data like Admin Users, we use React state arrays to simulate a database.

const handleDelete = (id) => {
    if (window.confirm('Are you sure you want to delete this user?')) {
      // Create a new array without the selected user
      setUsers(users.filter(u => u.id !== id));
    }
};

Tab Navigation (Inside Courses)

Instead of hard reloads, users switch views inside a course via React Router Links.

<Link 
  to={`/student/course/${id}/lectures`}

6. Navigation Flow

Since this is a Single Page Application (SPA), React Router handles the navigation invisibly. The browser doesn't request a new HTML file; JavaScript simply swaps the components.

The Routing Logic (App.jsx)

  1. The user hits / and sees the Public Landing Page.
  2. They navigate to /login and authenticate.
  3. The AuthContext updates to reflect their role (e.g., Student).
  4. React Router redirects them to /student.
  5. If they try to type /admin in the URL bar manually, the <ProtectedRoute allowedRoles={['student']}> catches them and renders an "Unauthorized" message.

Typical Flow

Login → Student Dashboard → Click Course Card → Read Lectures → Click Assignments Tab → Click Specific Assignment.

7. Styling & UI Design Approach

  • Tailwind CSS: We use utility classes directly in the JSX (e.g., className="flex items-center gap-4 p-5"). This isolates styling strictly to the component, preventing CSS collisions across pages.
  • Glassmorphism: Achieved using Tailwind's background opacities and blurs (e.g., bg-white/10 backdrop-blur-xl border border-white/20).
  • Layout System: Heavily reliant on CSS Flexbox (flex justify-between) for aligning navbars and buttons, and CSS Grid (grid grid-cols-3) for dashboard cards and layouts.
  • Dynamic Styling: We use tailwind-merge (twMerge) to conditionally apply classes, such as highlighting an input box red if a validation error exists.

8. Key Front-End Concepts Used

  • Component-Based Architecture: Everything is a component. If a piece of UI is used more than twice (like a Button), it is extracted into a standalone function that accepts properties (Props).
  • State Management (useState): Holding data that changes over time inside a component (like what the user is typing, or whether a modal is open or closed).
  • Global Context API: Passing data (like user authentication status) down through the entire application without having to manually pass props through every single layer.
  • Client-Side Routing: Updating the URL and changing the view immediately using JS, resulting in a significantly faster, native-app-like feel.

9. Discussion Q&A (Prep)

Q: "How does the UI respond to user actions?"

A: The UI responds via React's state mechanisms. When a user clicks a button or types in an input, an Event Handler fires, updating the state. React detects this state change and efficiently re-renders only the changed portion of the DOM (Virtual DOM).

Q: "How is dynamic data/state handled?"

A: Local data, like form inputs or modal toggles, is handled using the useState hook. Global data, like the logged-in user's role, is managed using the React Context API, making it accessible to any component, such as our layout headers.

Q: "How are components structured?"

A: We follow an atomic design approach. Base generic elements (Buttons, Inputs, Cards) sit in components/ui. Role-specific Layout wrappers sit in layouts/. These are combined inside of pages/ to create the final views.

Q: "How is navigation implemented?"

A: We use react-router-dom. The App.jsx file acts as our router configuration map. Instead of traditional <a href="..."> tags, we use React Router's <Link to="..."> component, which intercepts the click and changes the component locally without requesting a new webpage from a server.
